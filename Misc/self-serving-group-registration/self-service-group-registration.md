# Self-service group registration

Status: **draft for discussion**\
Author: Kai Jaeger

This document proposes replacing the manual process for creating a group on a Tatin registry with a fully automated one.

Nothing has been implemented yet. The purpose of this document is to agree the design before code is written.


## The problem

Today a new user must email me as the registry operator (referred to as "the operator" in the remaining document). The operator then:

1. Creates a group according to the user's wishes
2. Invents an API key for that group
3. Installs the key on the server by writing `Credentials.txt`
4. Emails the key back to the user

Only then can the user visit the group home page, enter a description and an email address, and save both by supplying the API key.

This is slow, it does not scale, it costs the operator time for every single user and the key travels by email in clear text. 


## Goals

- A user can register a group without any human intervention
- Introduce a password along with an API key
  - the password is used to manage the data on the Tatin server
  - the API key is used to publish etc. packages
- Ownership of the group is tied to a verifird email address
- A user can replace her API key on her own, should it leak
- A user who has lost her password can recover access on her own
- Everything that works today keeps working, with no migration step on the server


## Non-goals

These are deliberately out of scope for this proposal. They are listed so that we can agree they are out of scope.

- Several API keys per group. Deferred deliberately for the sake of a simpler first version; [The API key](#) explains what it would cost to add later
- Transferring ownership of a group from one person to another
- More than one owner per group
- Scoping an API key to particular packages
- Automatic expiry of API keys
- Single sign-on by way of GitHub or similar


## Overview

Two secrets, with different jobs:

| Secret | Created by | Used for | Where it lives |
|:-------|:-----------|:---------|:---------------|
| Password | Chosen by the user | Web pages only: edit the home page, manage keys, change email | Hashed, in the group record on the server |
| API key | Generated by the server | Publishing and deleting packages | Hashed on the server; clear text in the user's Tatin client settings |

Keeping them apart matters. The API key is stored in clear text in the client's user settings (see `api_key` in the documentation on user settings), so it should be a value the server invented and nobody has to remember. The password is a value the user remembers, and it never leaves the browser.

This also means the client side does not change at all. A user still puts a server-generated key into `api_key`, exactly as today.


## Registration

The user visits a *Register a group* page and works through four steps. The steps are separate HTTP requests. There is no session: each step carries a token in a hidden field that identifies the pending registration on the server.

### Step 1: choose a group name

The user enters a name. The server checks that it:

- Matches `^[A-Za-z]+[A-Za-z0-9_]*$`, the same rule that already governs the group part of a package ID
- Is not on a small list of reserved names
- Is not taken

"Taken" is the union of four sources, compared case insensitively because package IDs are compared that way too:

- Groups that already own packages, from the registry index
- Groups that appear in `Credentials.csv`
- Groups that own a home page, meaning there is a record for them
- Groups that are the subject of an unexpired pending registration

### Step 2: give an email address

The server generates a code, stores the pending registration and emails the code to the address given. The reply asks for the code.

### Step 3: enter the code

The server checks the code against the pending registration. If it matches, and has not expired, and the attempt limit has not been reached, the registration is marked as verified.

### Step 4: describe the group and choose a password

The user supplies the text for the group home page and a password of at least ten characters. The server then, in one go:

- Writes the group record with the home page text, the email address and the hash of the password
- Generates the API key and writes its rule to `Credentials.csv`
- Displays the API key **once**, with an explanation that it cannot be shown again

The pending registration is deleted.


## The API key

Each group owns exactly one API key. The group home page gains a *Manage access* button, leading to a page that asks for the password and then offers three things:

- **Regenerate the API key.** The server invents a new key, replaces the stored hash and shows the clear text once. The old key stops working the moment the new one is written.
- **Change the email address.** The new address has to pass the same code check as at registration before it takes effect.
- **Change the password.**

The key is never shown again after it has been created. A user who mislays it regenerates it and updates her client settings.

Should several keys per group be wanted later, the shape of the change is known and it is not large. `Credentials.csv` gains a fourth column for a key name and a group owns as many rows as it has keys; rows written before that point default their name to the group name, so nothing on disk needs converting. 

The one piece of code that has to change is `AcceptCredential`, which today finds a group's rule with `groupNames⍳⊂groupName`, finding only the first one.


## Forgotten password

The same code mechanism, keyed on the group name:

1. The user asks to reset the password for a named group
2. The server sends a code to the email address on file for that group
3. On success the user chooses a new password

The email address is never displayed and never accepted as input here. A person who does not already control that mailbox learns nothing and gains nothing.

Resetting the password does **not** invalidate the API keys. They are independent, and revoking an API key is a separate deliberate act.


## Data model

Three pieces of state. Two of them already exist.

### Credentials.csv

Unchanged, one rule per group:

```
group,hash,salt
```

The format stays as it is, no file on disk is touched and `AcceptCredential`, `ReadCredentialFile` and `ConvertCredentials` are all left alone. The `Credentials.txt` drop-in that the operator uses keeps working exactly as documented.

One thing is new, though. Until now this file is only ever written when the operator drops a `Credentials.txt` beside it. Registration and key regeneration have to add or replace a single rule directly, so the server needs to write the file itself. That write has to be held against concurrent requests, and it interacts with housekeeping, which watches the file's timestamp and rereads the credentials whenever it changes. Rereading after our own write is harmless, and in fact convenient.

### The group record

The record that already holds the home page text and the email address gains two more fields, for the password hash and its salt. The component file that holds it was created with six spare components, so there is room without changing its shape.

Groups that have no password yet are the normal case on the day this ships. They keep working: where a password is asked for, a valid API key is accepted instead, and the page invites the user to set a password. That is the migration path, and it needs no action from the operator.

A group whose record has no email address cannot use the password reset. Those users still have to write to the operator, as they do today.

### Pending registrations

One small file per pending registration, in a `Pending` folder, named after its token:

| Field | Meaning |
|:------|:--------|
| `group` | The name being registered |
| `email` | Where the code was sent |
| `purpose` | `register` or `reset` |
| `codeHash`, `salt` | YYYY-MM-DD |
| `expiresAt` | Dyalog date number |
| `attempts` | Incremented on every wrong guess |
| `ip` | For rate limiting |

Housekeeping deletes expired files. 

## Security

### The code is six digits

A million possibilities, for a code that lives ten minutes. That is ample on its own.

### Throttling access

The code carries most of the weight itself, but guesses are still capped: **five wrong ones and the code is destroyed**, and the user starts again. At six digits this is less about the odds of a lucky guess than about denying an attacker a cheap way to keep a pending registration alive and to generate load.

Failed password attempts need throttling too, with a growing delay. Unlike a code, a password does not expire, so an attacker can take as long as he likes over it.

### Salting

A salt defeats precomputed tables and stops one cracked hash from revealing password reuse across groups. It does nothing against guessing one particular password.

The current hash is a single unstretched SHA-256 pass, which is fast. A weak password falls quickly to an attacker who has the file.

So the ten character minimum is worth having, and the things that actually protect the account are:

- Throttling failed attempts, both for passwords and for codes
- Transport encryption, so that neither the password nor the code can be read off the wire


### Rate limits

| What | Limit |
|:-----|:------|
| Wrong codes per pending registration | 5, then the code dies |
| Codes requested per email address | 3 per hour |
| Codes requested per IP address | 10 per hour |
| Failed password attempts per group | Throttled, with a growing delay |

The per-email and per-IP limits exist because the registration form makes the server send mail to an address that an anonymous caller chose. Step 2 cannot be authenticated: proving that the caller controls the mailbox is the very thing the code is there to establish, so at the moment the mail goes out the server does not know who asked.

Without limits, anyone can script the form and aim your server at a victim's inbox. Three things follow, in rising order of seriousness:

- The victim's mailbox fills with verification codes. Each one costs the attacker a single HTTP request
- The resulting bounces and spam complaints put the reputation of the sending account at risk. The likely damage is not that somebody sends spam through us, it is that **we lose the ability to send mail at all**, which would cost us crash reports and publish notifications along with the codes themselves
- Sending is a blocking call, so every request occupies a thread for the length of an SMTP conversation. With `MaxNoOfThreads` at 64 it does not take many concurrent requests to starve the server of threads for ordinary traffic.


### The verification email

Two details of how that mail is composed matter.

**The group name has to be validated before any mail is composed.** It is attacker-controlled and it will appear in the subject or the body. To be checked against `^[A-Za-z]+[A-Za-z0-9_]*$`.

**The email address has to be rejected if it contains a control character.** A CR or LF smuggled into the recipient field is the classic way to inject a header of one's own, adding a `Bcc:` or replacing the body. This check belongs next to the address validation.

### Transport

Registration, password entry and code entry must not be available over plain HTTP. On a server that terminates TLS elsewhere, this means trusting the reverse proxy's forwarded protocol header. The endpoints should refuse to serve when the connection is not secure, with the check configurable for local development.

### Name squatting

Automated registration invites somebody to register `dyalog`, `aplteam` and every other name worth having, using throwaway addresses. Email verification does not prevent this; it only makes it slightly tedious.

Several options, none of which is obviously right:

- Do nothing and deal with it if it happens
- Reclaim a group that has published no package within some number of days
- Keep a reserved list of names that only the operator can hand out
- Require a first package within some period, else the registration lapses

This wants a decision, and it is a policy decision rather than a technical one.


## Configuration

A new section in the server's INI file. Self-service is **off** by default, so that existing servers behave exactly as they do now until the operator turns it on.

```
[REGISTRATION]
Active              = 0     ; 1 enables self-service registration
CodeLength          = 6
CodeLifetime        = 10    ; minutes
MaxAttempts         = 5     ; per code, then it is destroyed
MinPasswordLength   = 10
MaxPerEmailPerHour  = 3
MaxPerIpPerHour     = 10
RequireSecure       = 1     ; refuse to serve these pages over plain HTTP
```


## What this touches

For an estimate of the blast radius:

| Area | Change |
|:-----|:-------|
| Credentials file | Written directly by the server, not only through the operator's drop-in file |
| Request routing | New pages, some of which must bypass the credential check that currently guards every POST |
| Form handling | The current parser assumes one particular form. It needs generalising |
| Group record | Two more fields, for the password hash and its salt |
| Housekeeping | Sweep expired pending registrations |
| Email | One new message, the verification code |
| Group home page | Password instead of API key, and a link to managing access |
| Documentation | The page on securing a registry, plus a new page for users |
| Test cases | A new group of server tests |

Because a group still owns exactly one API key, none of the code that reads or checks credentials changes at all. That is the benefit of deferring multiple keys, and it is worth a good deal: `AcceptCredential` is the function that decides who may publish.
